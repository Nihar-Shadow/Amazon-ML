# Matching System Design

## Design Goal

Resolve business entities across:

```text
Source 1 ↔ Source 2
Source 1 ↔ Source 3
```

using only supplied challenge data.

## Design Priorities

Ordered as engineering priorities, not political/evaluative rankings:

1. Correctness
2. Candidate recall
3. Precision
4. Scalability
5. Reproducibility
6. Interpretability

The final model selection must be determined experimentally.

## Entity Representation

Each record:

```text
ID
Name
Address
Country
```

Keep original text.

Create derived normalized representations separately.

## Name Design

Names can differ because of:

- capitalization
- punctuation
- abbreviations
- legal suffixes
- spelling errors
- token order
- web domains
- transliteration
- regional scripts

Therefore one name similarity metric is insufficient.

## Address Design

Addresses can differ because of:

- abbreviations
- component ordering
- missing components
- missing complete address
- city/state formatting
- postal information
- landmarks
- regional scripts

Address evidence should be robust to missing fields.

## Country Design

Country is useful for narrowing candidate space.

However:

- train contains US and India
- test additionally contains France

Therefore country handling must be open-set.

## Blocking Design

Use multiple blocks.

Conceptually:

```text
Block 1: exact_name (exact compact normalized name)
Block 2: sorted_name_tokens (order-invariant token set)
Block 3: first_two_name_tokens (prefix token bigram)
Block 4: longest_name_token (salient distinctive token)
Block 5: name_prefix_6 (prefix character stub)
Block 6: name_address_combo (name token + address number)
Block 7: address_exact_combo (address number + address token)
Block 8: name_leet_compact (leetspeak digit/symbol normalization)
Block 9: name_dba_alias (trade name / DBA / doing-business-as alias)
Block 10: address_salient_combo (address number + salient locality/city token)
```

Take the union of candidates.

Then deduplicate.

## Why Multiple Blocks?

A single blocking key can fail when:

- business name is transformed into a domain
- address is missing
- name contains a typo
- script changes
- tokens are reordered

The union of independent blocks protects recall.

## Candidate Refinement Design

Broad multi-block union generates high recall but introduces redundant candidate pairs.
To ensure the ML model receives a computationally feasible, high-signal candidate set:

```text
Broad Candidate Pool (Union of Blocks)
                ↓
    Candidate Refinement Engine
  (Heuristic Scoring: n-gram, token Jaccard,
   containment, address similarity, number overlap)
                ↓
    Provenance Bypass (Preserve Exact Matches)
                ↓
    Top-K Capping (max 50 candidates per S1)
                ↓
    FINAL CANDIDATE SET (output/candidate_pairs.tsv)
                ↓
         ML Matching Model
```

`candidate_pairs.tsv` represents the exact final candidate set immediately preceding the ML model.

## Feature Engineering Design (Phase 4)

Candidate pairs generated by EXP-013 are transformed into structured 87-dimensional feature vectors (`phase4-v1` schema):

```text
FINAL CANDIDATE PAIR (S1, S2/S3)
                ↓
    PairwiseFeatureExtractor
    ├── Group 1: Name Similarity (15 features: exact, compact, token Jaccard, 2/3/4-grams, Levenshtein, prefix/suffix)
    ├── Group 2: Address Similarity (15 features: exact, token Jaccard, 3/4-grams, numbers, locality, postal)
    ├── Group 3: Cross-Field Interactions (8 features: strong/weak combinations, number+name, agreement count)
    ├── Group 4: Open-Set Country (4 features: exact, normalized, missing, conflict)
    ├── Group 5: Multi-View Representations (5 features: leet exact/sim, DBA match, compact matches)
    ├── Group 6: Blocking Provenance (11 features: 10 strategy indicators + strategy count)
    ├── Group 7: Refinement Heuristics (7 features: composite score, n-gram, token, containment, address)
    ├── Group 8: Record Quality & Artifacts (16 features: lengths, tokens, missingness, non-Latin, URL, legal)
    └── Group 9: Cardinality / Frequency (6 features: fitted strictly on training entities)
                ↓
    Structured Pairwise Feature Vector (87 features, 0% leakage, 0 NaN/Inf)
                ↓
          ML Matching Model (Phase 5)
```

## Matching Design

For each candidate:

```text
name evidence
+
address evidence
+
country evidence
+
token evidence
+
missingness indicators
+
other validated features
```

The model produces a match score.

## Decision Design

A candidate is not automatically a match merely because it was generated.

The decision layer operates with a calibrated threshold:

```text
Score >= 0.70  → MATCH (included in prediction set)
Score < 0.70   → NON-MATCH (pruned)
```

The threshold of 0.70 was selected via fine-grained validation sweep, maximizing entity-level Macro F0.5 at 0.9333 while suppressing false positives (Macro Precision: 0.9646).

## Singleton Design

Some S1 entities genuinely have no target matches.

Therefore:

```text
No sufficiently strong candidate
        ↓
empty match list
```

is a valid prediction.

Do not force at least one match.

## Post-processing

Post-processing must be conservative.

Potential constraints may include:

- duplicate target assignment
- implausible score combinations
- unsupported country mismatches

But a training observation must not automatically become a hidden-test guarantee.

Every post-processing rule requires validation evidence.

## Output Design

For every test S1:

```text
source1_entity_id    matched_entity_ids
```

If no matches:

```text
S1-XXXXX    
```

Candidate output:

```text
source1_entity_id    candidate_entity_ids
```

Every final match must occur in the candidate list.

## Phase 6 Production Inference & Package Design

1. **Partitioning Architecture:**
   Country-wise processing (`France`, `US`, `India`) guarantees $0.00\%$ cross-country loss while bounding memory consumption to $< 800$ MB RAM.
2. **Subsetting Invariant:**
   `matching_results.tsv` strictly draws from `candidate_pairs.tsv` at threshold $\theta = 0.70$.
3. **Reproducible Submission Package:**
   Packaging script produces `<team_name>_submission.zip` with clean separation of outputs, source code, and methodology documentation.
